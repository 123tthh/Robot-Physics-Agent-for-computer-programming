# Codex 工作规划与任务协议

本文规定如何使用仓库中的 Markdown 规划 Codex 工作。目标是让每次开发任务边界明确、可独立验证，并能在新的 Codex 会话中继续。

## 1. 每次任务的阅读顺序

Codex 开始工作前应依次阅读：

1. 根目录 [`AGENTS.md`](../AGENTS.md)；
2. [`overview.md`](overview.md)；
3. 本文；
4. [`phases/README.md`](phases/README.md) 中当前阶段；
5. 当前任务对应的阶段文件；
6. 阶段文件列出的相关技术文档和代码。

不要要求 Codex 一次性阅读所有外部项目或实现所有阶段。

## 2. 状态约定

阶段和任务使用以下状态：

| 状态 | 含义 |
|---|---|
| `DONE` | 产物存在，验收命令和门槛均通过 |
| `PARTIAL` | 已有接口或模拟实现，但阶段门槛尚未通过 |
| `READY` | 前置阶段满足，可以领取 |
| `BLOCKED` | 缺少明确的外部资产、硬件信息或权限 |
| `PLANNED` | 尚未开始，且依赖未完全满足 |

文档中的状态是规划快照。Codex 完成任务后应更新任务状态、完成证据和剩余风险，而不是只勾选复选框。

## 3. 任务粒度

一个 Codex 任务应满足：

- 只属于一个阶段，最多修改一个主要能力边界；
- 有稳定任务编号，例如 `P1-T03`；
- 可以在一次任务中实现和验证；
- 明确列出不做什么；
- 包含至少一个自动化验收或可复现的人工验收；
- 不以“接入整个 Isaac Sim”“完成真机控制”等开放目标作为单个任务。

如果任务同时跨越 Runtime、Isaac、语音、导航和真机，应先拆分 Adapter 契约、替身实现和单独集成任务。

## 4. Codex 任务模板

启动新任务时可直接复制以下提示词，并替换方括号内容：

```text
请先阅读 AGENTS.md、docs/overview.md、docs/CODEX_WORKPLAN.md、
docs/phases/README.md 和 [阶段文件]。

执行任务：[任务编号和名称]

目标：
[一个可验证的结果]

范围：
- [允许修改的模块]
- [需要新增的接口/测试/文档]

不在范围：
- 不提前实现后续阶段；
- 不让 Agent 输出关节/力矩命令；
- 不用控制器声明替代 Verifier 证据；
- 不把重型仿真或厂商依赖导入核心领域模型。

验收：
- [任务特定命令或场景]
- make check
- make demo

完成后：
1. 汇总改动、验证结果和剩余风险；
2. 更新对应任务状态和完成证据；
3. 不自动开始下一个阶段。
```

## 5. Codex 的实现规则

### 5.1 先契约，后实现

新增能力时优先确定：

```text
Skill 名称
+ 输入参数
+ 前置状态
+ 局部后置状态
+ 下一技能就绪状态
+ 独占资源
+ 失败码
+ 恢复 Skill
+ Evidence 来源
```

再实现模拟 Adapter，最后接真实系统。

### 5.2 Oracle 与最终观测分离

Isaac 真值、Pygame 内部事件、文件 API 可以作为开发 Oracle，但论文评测必须能切换到与真机一致的视觉、接触、OCR 和测试证据。两者必须使用不同的 `source`。

### 5.3 依赖隔离

- `src/vskill_os` 核心尽量保持标准库可运行；
- Isaac Sim、ROS 2、DDS、ASR、LLM 和厂商 SDK 放在可选 Adapter 或独立进程；
- 不同 Isaac/Isaac Lab 版本使用独立环境，通过协议连接；
- 模型权重必须有版本、许可证、哈希和兼容性 Manifest。

### 5.4 完成声明

Codex 不能因为单元测试通过就宣称真机能力完成。报告必须区分：

- 领域契约已实现；
- 纯 Python 模拟已验证；
- Isaac 动力学已验证；
- 硬件在环已验证；
- 真机已验证。

## 6. 阶段总表

| 阶段 | 当前状态 | 核心退出条件 |
|---|---|---|
| P0 Runtime 与证据基线 | `DONE`/持续维护 | 非法状态不能推进；故障可恢复；测试通过 |
| P1 混合仿真底座 | `DONE` | Isaac 5.1 中 G1 mode 15/5010 + 双 Dex3、四墙房间/三工位/导航锚点、74 键带标识 PhysX 接触、三路 RTX 相机与 PTY 已闭环 |
| P2 双手多指键盘 | `PARTIAL` | 纯 Python 与自动事件门禁已通过，GUI 可见实体触键待复核 |
| P3 代码 Agent 闭环 | `PARTIAL` | 真实隔离代码任务完成失败—修复—复测 |
| P4 坐下、椅子与工作姿态 | `PARTIAL` | 坐姿稳定、屏幕可见和双手可达联合通过 |
| P5 导航与本地语音 | `PARTIAL` | 语音目标可触发导航和任务图，且无低层越权 |
| P6 Sim-to-real 与自改进 | `PLANNED` | 真机安全门槛、对照实验和受约束技能更新通过 |

## 7. 通用 Definition of Done

一个任务只有同时满足以下条件才可标记 `DONE`：

1. 代码、配置或文档产物已经存在；
2. 新接口有最小可运行实现或明确替身；
3. 正常、失败和恢复路径至少各有一个测试；
4. Verifier 使用独立证据，而非复述控制器状态；
5. 失败码能定位原因且不会静默降级；
6. 运行 `make check` 与 `make demo`；
7. 文档说明能力等级和未验证部分；
8. 没有覆盖用户已有的无关改动。

## 8. 任务结束记录模板

每个阶段文件末尾可追加：

```text
完成记录：
- 任务：P?-T??
- 状态：DONE / PARTIAL / BLOCKED
- 修改：文件或模块
- 验证：命令、场景和结果
- 能力等级：契约 / 纯 Python / Isaac / HIL / 真机
- 剩余风险：
- 下一可领取任务：
```
